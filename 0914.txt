온프레미스 서버에서는 php-fpm 프로세스와 확장 로드 여부를 이렇게 확인합니다.

1. php-fpm 프로세스 확인

ps -ef | grep '[p]hp-fpm'
systemctl status php-fpm      # 배포판에 따라 php8.x-fpm, php-fpm82 등

master 1개와 worker 여러 개가 보이면 살아 있는 것입니다.

2. qslp 확장 로드 확인 (CLI)

php -m | grep -i qslp
php -r 'var_dump(extension_loaded("qslp"));'
php --ri qslp
php -r 'print_r(get_extension_funcs("qslp"));'

qslp가 출력되고 bool(true)면 로드된 것입니다.

3. php-fpm 프로세스에 실제로 올라갔는지 확인

CLI와 php-fpm이 다른 php.ini를 읽을 수 있어서, 실제 웹 프로세스의 메모리 맵을 봅니다.

# php-fpm 프로세스 중 qslp.so 를 매핑한 것이 있는지
for p in $(pgrep php-fpm); do grep -l qslp.so /proc/$p/maps 2>/dev/null; done

# 또는 lsof
lsof -p $(pgrep -o php-fpm) | grep qslp

php-fpm PID 목록이 찍히면 워커에 확장이 올라간 것입니다. 아무것도 안 나오면 php-fpm이 읽는 ini에 등록이 안 됐거나 재시작 전입니다.

4. 안 나올 때 점검할 것

# php-fpm이 읽는 ini 위치와 등록 여부
php-fpm -i 2>/dev/null | grep -i 'loaded configuration\|additional .ini'
grep -rn 'qslp' /etc/php* 2>/dev/null

# 확장 파일이 확장 디렉터리에 있는지
ls -l "$(php-config --extension-dir)/qslp.so"

# 확장 로드 실패 로그
grep -i qslp /var/log/php-fpm/*.log /var/log/php*/*.log 2>/dev/null | tail

ini에 extension = qslp를 추가한 뒤에는 php-fpm 재시작이 필요합니다(systemctl restart php-fpm).

5. 동작까지 확인하려면

앱 코드가 배포된 경로에서 왕복 회귀 스크립트를 돌립니다.

php {앱루트}/extmod/keypad/_test/aton_qslp_roundtrip.php

프로세스 확인
ps -ef | grep CertVerifyServer | grep -v grep
java -Dfile.encoding=UTF-8 -cp out:lib/* CertVerifyServer 줄이 나오면 떠 있는 것입니다. 안 나오면 Java 전체를 확인하세요.
ps -ef | grep java | grep -v grep

포트 확인 (8290 LISTEN 여부)
ss -ltnp | grep 8290
ss가 없으면 netstat -ltnp | grep 8290을 쓰시면 됩니다. LISTEN 줄 끝에 java PID가 같이 보입니다.

응답 확인
curl -v -m 5 http://localhost:8290/
WAS와 다른 서버에 떠 있다면 WAS 서버에서 설정된 주소로 확인하세요.
curl -v -m 5 http://172.18.20.110:8290/
Connection refused면 프로세스 미기동, 타임아웃이면 방화벽이나 네트워크 문제입니다.

서비스로 등록돼 있다면
systemctl list-units --type=service | grep -i cert
systemctl status <서비스명>

로그 확인 (기동 위치 기준, 보통 실행 디렉터리의 로그 파일이나 nohup.out)
ls -l /proc/$(pgrep -f CertVerifyServer)/cwd
이 명령으로 실행 디렉터리를 찾은 뒤 그 안의 로그 파일을 tail -f로 보시면 됩니다.

***  리눅스 환경에서 testdir.crosscert.com (testdir.crosscert.com) 포트 389 ,한국전자인증 TESTCA 로 tcp 통신이 되는지 확인

1. DNS 확인

getent hosts testdir.crosscert.com

2. TCP 389 접속 확인 (가장 간단)

nc -zv -w 5 testdir.crosscert.com 389

성공이면 succeeded! 또는 open, 실패면 Connection timed out / refused 가 나옵니다. nc 가 없으면 sudo apt install netcat-openbsd.

3. nc 없이 bash 내장 기능으로

timeout 5 bash -c '</dev/tcp/testdir.crosscert.com/389' && echo OPEN || echo BLOCKED

4. 실제 LDAP 응답까지 확인 (선택)

sudo apt install -y ldap-utils
ldapsearch -x -H ldap://testdir.crosscert.com:389 -b "" -s base -l 5

TCP만 열린 게 아니라 LDAP 서버가 응답하는지까지 봅니다. Can't contact LDAP server 면 차단입니다.

5. 관련 호스트 한꺼번에 점검

인증서 발급(CMP)은 testca.crosscert.com:4502, 운영 디렉터리는 dir.crosscert.com:389 를 씁니다.

for h in testdir.crosscert.com:389 dir.crosscert.com:389 testca.crosscert.com:4502; do
  timeout 5 bash -c "</dev/tcp/${h%:*}/${h#*:}" && echo "$h OPEN" || echo "$h BLOCKED"
done

참고

- 검증서버가 도커로 떠 있다면 호스트에서 열려도 컨테이너 안에서 다시 확인해야 합니다. docker exec crosscert bash -c 'timeout 5 bash -c "</dev/tcp/testdir.crosscert.com/389" && echo OPEN || echo BLOCKED'
- 서버에 프록시 환경변수(http_proxy 등)가 있어도 LDAP은 프록시를 타지 않으므로 방화벽 아웃바운드 389 허용이 필요합니다.
